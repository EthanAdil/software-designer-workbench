05 · 软件工程（上午 12 题 · 第一大模块）

上午卷分值最高的单模块，也是下午 DFD/UML 题的基础。四张表必须默写：开发模型对比、耦合 7 级、内聚 7 级、覆盖强度排序。项目管理部分重点抓关键路径手算。

二、开发模型

2.1 模型对比

模型核心特征适用场景主要缺点
瀑布阶段严格串行、文档驱动需求明确稳定、团队熟悉领域难以响应变更，后期才见产品
原型快速构建可运行版本澄清需求需求不明确原型可能被误当产品
增量分批交付可用版本可分块交付、希望早见效需良好架构规划
螺旋增量 + 原型 + 风险分析大型、高风险项目成本高、需风险评估能力
V 模型开发与测试一一对应强调测试与验证的项目灵活性差
喷泉面向对象、迭代无缝、无间隙OO 项目管理难度大
敏捷/Scrum迭代 sprint、可工作软件优先需求多变、小团队文档少、依赖团队素质
RUP用例驱动、以架构为中心、迭代增量中大型 OO 项目重量级、裁剪复杂

V 模型对应关系：需求分析 ↔ 验收测试；概要设计 ↔ 系统测试；详细设计 ↔ 集成测试；编码 ↔ 单元测试。口诀"需求验、概系、详集、编码单"。

螺旋模型四象限：制定计划 → 风险分析 → 实施工程 → 客户评估。每转一圈完成一个增量，风险分析是它区别于增量模型的标志。

2.2 敏捷与 Scrum

敏捷宣言四条价值观：个体与交互高于流程与工具、可工作软件高于详尽文档、客户合作高于合同谈判、响应变化高于遵循计划。

Scrum 要素内容
三种角色Product Owner（需求与优先级）、Scrum Master（流程与障碍）、开发团队（交付增量）
三个工件Product Backlog、Sprint Backlog、增量
四个会议Sprint 计划会、每日站会、Sprint 评审会、回顾会

XP（极限编程）核心实践：结对编程、测试驱动开发 TDD、持续集成、小版本发布、重构、简单设计。

2.3 RUP

四阶段：初始（Inception）→ 细化（Elaboration）→ 构建（Construction）→ 交付（Transition）。

三大特点：用例驱动、以架构为中心、迭代与增量。每个阶段都有里程碑，细化阶段结束时架构基线确定。

2.4 模型选择

  • 需求稳定、合同明确 → 瀑布；
  • 需求模糊、需要用户参与 → 原型；
  • 大型高风险、需要早期识别风险 → 螺旋；
  • 需求频繁变化、小团队 → 敏捷；
  • 强调测试与验证 → V 模型。

三、需求工程

3.1 需求分类

类型内容例子
功能需求系统必须提供的功能订单支付、库存扣减
非功能需求性能、安全、可用性、可维护性响应时间 < 2 秒、支持 1000 并发
设计约束技术选型、法规、平台限制必须使用国产数据库、符合等保三级

非功能需求比功能需求更难验证，也更容易被忽视，考试常问"响应时间属于哪类需求"。

3.2 需求获取方法

访谈、观察（现场跟班）、问卷、原型、联合应用开发（JAD）、文档分析、头脑风暴。

选择依据：用户数量多 → 问卷；业务流程复杂 → 观察 + 访谈；需求不明确 → 原型；需要快速达成共识 → JAD。

3.3 DFD 与数据字典

DFD 四要素：外部实体、加工（处理）、数据存储、数据流。DFD 不描述控制流，控制流由状态图或流程图表达。

分层与平衡：父图中某个加工的输入输出，必须与其子图的输入输出保持一致（父子平衡）；子图内部的数据流可以细化，但不能凭空增加与父图不一致的外部输入输出。

数据字典符号：

符号含义
=定义为
+顺序连接
[ ]选择其一
{ }重复
( )可选

3.4 需求管理

  • 需求跟踪：正向跟踪（需求 → 设计 → 代码 → 测试用例）、逆向跟踪（测试用例 → 需求），确保每条需求都被实现和验证。
  • 需求变更控制：变更申请 → 影响分析 → CCB（变更控制委员会）审批 → 实施 → 验证 → 更新基线。
  • 需求基线：经过评审确认、作为后续开发依据的需求集合，变更必须走流程。

四、结构化设计

4.1 耦合（由低到高，越低越好）

级别名称含义例子
1非直接耦合模块间无直接联系两个独立模块
2数据耦合只传简单数据参数传一个整数
3标记耦合传整个数据结构传学生记录
4控制耦合传控制信息传标志位决定分支
5外部耦合共同访问外部环境/设备共用通信协议
6公共耦合共同访问全局数据区共用全局变量
7内容耦合直接访问对方内部数据或代码直接改对方私有变量

判断技巧：看"传的是什么"——简单值 → 数据耦合；结构体/记录 → 标记耦合；标志/开关 → 控制耦合；全局区 → 公共耦合；内部实现 → 内容耦合。

4.2 内聚（由高到低，越高越好）

级别名称含义
1功能内聚所有元素共同完成单一功能，缺一不可
2顺序内聚元素顺序执行，前一输出是后一输入
3通信内聚元素操作同一数据结构
4过程内聚元素按特定次序执行，但无数据传递
5时间内聚元素在同一时间段执行（如初始化）
6逻辑内聚元素逻辑相似，由参数选择执行
7偶然内聚元素间无实质联系

判断技巧：能否用一句话概括"这个模块只做一件事"——能则是功能内聚；元素之间有数据流则是顺序/通信；只是时间上一起做则时间内聚；靠参数选择不同功能则逻辑内聚。

4.3 模块化指标

  • 扇入：被多少个上级模块调用，越大说明复用性越好；
  • 扇出：调用多少个下级模块，宜控制在 3~4，过大说明模块过于复杂；
  • 深度：控制层次的最大层数；
  • 宽度：同一层最多的模块数；
  • 作用域：模块的影响范围；控制域：模块的控制范围。要求作用域应在控制域之内。

4.4 结构图与设计方法

结构图描述模块的调用关系：矩形表示模块，箭头表示调用，带箭头的小圆表示传递的数据/控制信息。

从 DFD 导出结构图有两种分析方法：

方法适用 DFD做法
变换分析变换型（输入 → 变换中心 → 输出）找出输入、变换、输出三部分，分别映射为输入模块、变换模块、输出模块
事务分析事务型（事务中心按类型分派）找出事务中心，为每类事务建立一条处理分支

判断：DFD 中有一个加工根据输入类型选择不同处理路径 → 事务型；数据流呈"进来—加工—出去"的线性结构 → 变换型。

五、详细设计与复杂度

5.1 设计工具

工具特点
程序流程图直观，但容易违反结构化（箭头可任意跳转）
N-S 图（盒图）只允许顺序、选择、循环，强制结构化
PAD 图（问题分析图）自顶向下、层次清晰，适合逐步细化
判定表/判定树表达复杂条件组合，判定表更严谨
PDL（伪代码）接近自然语言，便于转换为代码

5.2 McCabe 环形复杂度

V(G) = 边数 - 结点数 + 2
     = 判定结点数 + 1
     = 区域数

V(G) 也等于达到基本路径覆盖所需的最少测试用例数。

例：流程图有 5 个判定结点 → V(G) = 5 + 1 = 6，至少需要 6 个测试用例覆盖所有基本路径。

六、软件测试

6.1 黑盒测试

方法思路适用
等价类划分把输入分成有效/无效等价类，每类取一个代表输入范围明确
边界值分析取边界及边界±1数值范围、长度限制
错误推测凭经验猜易错点补充其他方法
因果图/判定表输入条件组合 → 输出逻辑组合复杂
正交试验用正交表减少组合数多因素多水平

边界值是最高频的送分题：输入范围 1~100，测试数据取 0、1、2、99、100、101。

6.2 白盒测试与覆盖强度

语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖
覆盖要求
语句覆盖每条可执行语句至少执行一次
判定覆盖每个判定的真、假分支各至少一次
条件覆盖每个判定中每个条件的取值至少一次
判定/条件覆盖同时满足判定覆盖与条件覆盖
条件组合覆盖每个判定中条件取值的所有组合至少一次
路径覆盖所有可能路径至少一次

注意：条件覆盖不必然包含判定覆盖（每个条件都取到真假，但判定结果可能只出现一种），所以需要"判定/条件覆盖"这一更强的准则。路径覆盖最强，但路径数可能爆炸。

6.3 测试阶段

单元测试 → 集成测试 → 系统测试 → 验收测试
  • 单元测试：测单个模块，需要驱动模块（模拟调用者）和桩模块（模拟被调用者）。
  • 集成测试：自顶向下（需要桩）、自底向上（需要驱动）、三明治（两者结合）、大爆炸。
  • 系统测试：功能、性能、安全、兼容性等整体验证。
  • 验收测试：α 测试（开发环境，用户参与）、β 测试（用户环境，真实用户使用）。

回归测试：修改后重跑既有用例，确认未引入新缺陷。冒烟测试：快速验证基本功能可用，决定是否值得深入测试。

静态测试：代码审查、走查、静态分析，不运行程序。

七、维护与项目管理

7.1 软件维护

类型内容占比
改正性修复运行中发现的缺陷约 20%
适应性适应操作系统、硬件、数据格式变化约 25%
改善性/完善性新增功能、优化性能最大，约 50%+
预防性重构、提高可维护性较小

"改善性维护占比最大"是高频考点，不要凭直觉选改正性。

7.2 进度与关键路径

工具优点缺点
Gantt 图直观展示起止时间与并行难以表达任务依赖
PERT 网表达依赖、可算关键路径不如 Gantt 直观

关键路径计算：

  1. 正推求最早开始 ES、最早完成 EF（取所有前驱的最大值）；
  2. 逆推求最迟完成 LF、最迟开始 LS（取所有后继的最小值）；
  3. 总时差 = LS - ES = LF - EF；
  4. 总时差为 0 的活动组成关键路径，其长度即最短工期。

例：A(3)、B(4) 无前驱；C(2) 依赖 A；D(5) 依赖 B；E(3) 依赖 C、D。

7.3 成本估算与风险

成本估算方法：COCOMO（基本/中间/详细，按代码行估算）、Putnam（按工作量分布）、专家判断、类比估算、功能点 FP。

风险应对四种策略：

策略做法例子
规避改变计划，消除风险源不用不成熟技术
转移把风险后果转给第三方买保险、外包
减轻降低概率或影响提前培训、冗余设计
接受准备应急储备，不主动处理低影响风险

风险管理流程：识别 → 预测（概率与影响）→ 应对 → 监控。

7.4 配置管理与过程改进

配置管理五项：配置项识别、基线管理、版本控制、变更控制（CCB）、配置审计。

CMMI 五级：

级别名称标志
1初始级过程无序，靠个人能力
2已管理级项目级过程可重复、有基本度量
3已定义级组织级标准过程，项目按裁剪使用
4量化管理级用统计方法量化控制过程
5优化级持续改进，预防缺陷

7.5 软件质量模型

ISO 9126 六特性：功能性、可靠性、易用性、效率、可维护性、可移植性。

可维护性子特性：可理解性、可测试性、可修改性（易改变性）、稳定性、易分析性。

十、自检题

  1. 哪种模型以风险分析为核心？它包含哪四个象限？
  2. V 模型中"概要设计"对应哪一级测试？

  5. 流程图有 7 个判定结点，V(G) 是多少？
  6. 自顶向下集成需要哪种辅助模块？自底向上呢？
  7. 改善性维护与改正性维护哪个占比更大？
  8. 关键路径如何判定？总时差怎么算？
  9. CMMI 第三级的名称和标志是什么？
  10. 数据字典中 { }、[ ]、( ) 各表示什么？
  11. 变换分析与事务分析分别适用于什么 DFD？
  12. 需求变更控制的流程是什么？

答案与解析：
1) 螺旋模型；制定计划、风险分析、实施工程、客户评估。
2) 系统测试（需求↔验收、概要↔系统、详细↔集成、编码↔单元）。
3) 标记耦合（传的是数据结构而非简单值）。
4) 两者不可简单比较；条件覆盖不必然满足判定覆盖，故需要更强的判定/条件覆盖。
5) 7+1=8。
6) 自顶向下用桩模块；自底向上用驱动模块。
7) 改善性维护占比最大（约 50%+）。
8) 正推 ES/EF、逆推 LS/LF，总时差 LS-ES 为 0 的活动组成关键路径，长度为工期。
9) 已定义级；组织级标准过程，项目按裁剪使用。
10) { } 重复、[ ] 选择其一、( ) 可选。
11) 变换分析用于变换型（输入-变换-输出）；事务分析用于事务型（按类型分派）。
12) 变更申请 → 影响分析 → CCB 审批 → 实施 → 验证 → 更新基线。
